## 2. 렌더링: 왜 3D가 아닌가

### 2.1 구조
- 투영은 `lib/painters/isometric_painter.dart:43-54`의 1점 투시 6줄이 전부. 카메라 위치 고정, 회전 없음. `cameraYaw`, `toIso`, `isFaceVisible`(항상 true)은 죽은 코드이고 테스트가 이를 고정하고 있다.
- 깊이 버퍼, 법선, 광원 벡터, 컬링 없음. "조명"은 면마다 하드코딩된 `Color.lerp` 계수.
- 3,133줄 중 약 75%가 고정 시점 전용 장식: 카펫 섬유 400선, 벽 스크래치 80개, 12V 아웃렛, 카고 훅, 테일라이트(114줄), 번호판. 카메라가 움직이면 전부 못 쓴다.
- `vehicleName`(바닥 로고용), `trunkLipHeight`, `roofExtension`, `bumperDepth`, `bodyDepth`는 직렬화·테스트만 되고 어떤 페인터도 읽지 않는다.

### 2.2 정확성 버그
1. 옆면 가시성 반전. `lib/painters/box_renderer.dart:124-125`
   ```dart
   final showLeft = camX > x;        // 올바른 조건: camX < x
   final showRight = camX < x + w;   // 올바른 조건: camX > x + w
   ```
   중앙에서 벗어난 박스는 보여야 할 안쪽 면이 안 그려지고, 숨은 면의 모서리가 앞면 위에 선으로 남는다. 그래서 박스가 "앞면 사각형 + 윗면 조각"으로 납작하게 보인다.
2. 정렬 키가 앞쪽 z에만 지배됨. `lib/painters/guide_renderer.dart:48-49`
   ```dart
   (cz + cd) * 1000 + cy * 10 + cx
   ```
   z 1cm = y 1m와 같은 가중치. 지지 박스 위 뒤쪽에 얹힌 박스는 먼저 그려져서 아래 박스 윗면에 덮이고, 휠하우스(키 400)는 앞쪽 z가 0.40 미만인 인접 박스 위에 덮인다. 스크린샷에서 확인됨.
3. 개구부 프레임과 적재 실(sill)이 박스 뒤에 그려져야 하는데 항상 마지막에 그려져 박스를 덮는다. `lib/painters/vehicle_body_renderer.dart:88-99, 436-474`
4. 그림자는 박스 y와 무관하게 항상 바닥(y=-0.001)에 그려지고, 적층 박스의 그림자가 지지 박스 앞면 위에 찍힌다. `box_renderer.dart:63-85`
5. 시각 형상과 충돌 형상이 다르다. 벽은 바닥 테이퍼에서 천장까지 한 번에 기울어지는데 충돌은 60% 높이까지 수직 벽으로 계산한다. `lib/painters/trunk_renderer.dart:49-54` vs `lib/utils/collision.dart:47-52`

### 2.3 성능
- 정적 장면 캐시 없음. 드래그 중 포인터가 움직일 때마다 약 1,500 드로우, `Paint` 약 700개 할당, 그라디언트 셰이더 13개, 블러 4회를 다시 실행한다. 저사양 폰에서 드래그가 끊길 구조다.
- `shouldRepaint`는 `boxes` 리스트를 identity로 비교하는데 리스트는 항상 같은 인스턴스를 제자리 수정한다. 지금 다시 그려지는 이유는 `_updateCollisions()`가 매번 새 `Set`을 만들기 때문이다. 이 호출을 빠뜨리는 경로가 생기면 조용히 화면이 안 바뀐다. `isometric_painter.dart:106-115`, `lib/screens/simulator_screen.dart:2217-2219`

## 3. 인터랙션: 왜 동작이 안 되는가

1. 카메라 상수 불일치 (가장 큰 원인).
   페인터: `camY = h*0.85`, `focalLen = d*1.15` (`isometric_painter.dart:44-45`)
   화면: `camY = h*1.05`, `focalLen = d*1.0` (`simulator_screen.dart:825-826`, `894-895`)
   쏘렌토·800×600 캔버스 기준 개구부 쪽 바닥점이 약 95px 아래를 겨냥한다. 클릭이 빗나가고 드래그 델타 스케일이 틀린다. 투영 코드가 세 벌이라 생긴 사고이며, 화면은 페인터의 `toScreen`을 호출해야 한다.
2. 장비 추가 시 3cm 격자로 뿌림. `simulator_screen.dart:964-970`은 `gridUnit*3` 간격으로 분산하는데 `gridUnit`은 0.01이라 3cm다. 16개가 한 자리에 겹쳐 쌓이며 첫 화면부터 전부 빨간색이 된다. 사용자가 처음 보는 결과다.
3. 적층 드래그: 투영 평면은 드래그 시작 y에 고정인데 `_resolveStackingY`가 이동마다 y를 바꿔 커서와 박스가 분리된다. `simulator_screen.dart:710-719` (epic-status의 "P3-6 DONE"은 사실과 다름)
4. 히트테스트가 삽입 순서 역순·앞면+윗면만 검사해서 가려진 박스가 선택된다. `simulator_screen.dart:847-876`
5. Undo가 드래그를 되돌리지 못한다(이동 후에 스냅샷). 터치 첫 이동에 40px 점프. 박스를 건드리기만 해도 적재 순서 번호가 전부 지워진다. `simulator_screen.dart:672-679, 708-710, 733`
6. 장비 다이얼로그에서 서브카테고리를 바꾸면 선택이 초기화된다. 텐트 고르고 쿨러 탭으로 가면 텐트가 풀린다. `lib/widgets/add_box_dialog.dart:932, 964`
7. 도움말에 Q/E 카메라 회전이 적혀 있지만 구현이 없다. `lib/widgets/keyboard_shortcuts_dialog.dart:50-51`
8. 모바일: 자동배치·저장 다이얼로그가 400px 고정폭이라 360px 폰에서 넘친다. 온보딩은 새로고침마다 다시 뜬다. 자동저장이 없어 새로고침하면 전부 사라진다. `NotoSansKR` 폰트는 선언만 있고 번들이 없다.

## 4. 자동배치: 왜 판정을 믿을 수 없는가

- 지지 규칙이 네 벌이다: 화면 `_resolveStackingY`(가장 가까운 층), 화면 `_resolveGravity`, `auto_layout._findSupportY`(미커밋 재작성), `test/stacking_test.dart`의 복사본(가장 높은 층). 테스트는 배포 코드를 검사하지 않는다.
- 엔진 자체 `_canPlace`가 `CollisionDetector`와 다르다(테이퍼 무시 등). 그래서 엔진은 "성공"이라 하고 화면은 빨간 경고를 낸다.
- 극점(EP) 생성이 빈 바닥 뒤쪽(z 0.6~1.1m)을 후보로 만들지 못해 빈 바닥을 두고 공중에 띄운다.
- 미적재 박스를 `z = d + 0.05`(트렁크 밖)에 세워두고 충돌로 표시한다. 다음 조작에서 `clampTo`가 도로 안으로 끌어온다. `simulator_screen.dart:1600-1602`
- 이름과 달리 극점 알고리즘이 아니다. 배치된 박스의 모서리 6개를 그대로 후보로 쓰고(지지면으로 투영하지 않음), 지지 검사 없이 점수만으로 고른다. 휠하우스 윗면 시드 EP `(0.08, 0.30, 0)`의 y=0.30이 허공으로 그대로 전파되는 것이 공중부양의 직접 원인. `lib/models/auto_layout.dart:121-128, 365, 444-449`
- 회전이 yaw 0/90 두 가지뿐이다. 눕히기(lay-flat)가 없어서 접은 의자·폴대·테이블처럼 길쭉한 장비는 세워서만 시도하고 "적재 불가"가 된다. 캠핑 장비에서 가장 큰 오판 원인.
- 적용 직후 `snapToGrid(0.01)`을 하는데 `boxesOverlap`은 허용 오차가 0이라 부동소수점 반올림만으로 인접 박스가 충돌로 표시된다. 무작위 30개 × 20회 실험에서 충돌 표시 82건이 스냅 후 304건으로 늘었다. `simulator_screen.dart:1592`, `collision.dart:13-18`
- C필러 좁아짐 모델이 엔진(`y=0`부터 선형)과 충돌 판정기(천장 60%부터 선형)가 달라 엔진은 성공이라 하고 화면은 경계 밖으로 표시한다. `auto_layout.dart:413-422` vs `collision.dart:40-61`
- 세 전략의 적재율이 사실상 동률이라 "추천" 배지가 의미 없고, "들어갈까?" 빠른 판정은 균형 전략 하나만 돌린다. `simulator_screen.dart:1572, 2245-2257`
- 적재 순서 번호는 물리적 순서가 아니라 정렬 순서다. 안쪽 박스가 바깥 박스보다 늦은 번호를 받는 경우가 있다.
- 적재율 분모(907L)가 천장 드롭·테이퍼를 무시한다. 형상 함수를 적분하면 약 830L이고, 실제 MQ4의 공칭 적재량은 이보다 훨씬 작다. 공유 카드의 "적재율 %"가 이 위에 올라가 있다.
- 무게, 연질 여부(침낭·타프는 눌림), 접근성, 3열 폴딩, 테일게이트 개구부 통과 같은 현실 제약은 전혀 없다.

### 4.1 테스트 183개가 통과하는데도 고장인 이유
- `test/stacking_test.dart`는 화면의 private 메서드를 복사한 사본을 테스트한다. 사본은 "가장 높은 층"을 고르고 휠하우스를 무시하지만, 실제 화면은 "현재 y에 가장 가까운 층"을 고르고 휠하우스를 포함한다. 배포 코드는 검증되지 않는다.
- 자동배치 테스트는 엔진 자체 규칙으로 "겹침 없음·경계 안"만 확인한다. 지지(부양 없음), `CollisionDetector` 기준 유효성, 적용 후(스냅 후) 상태는 검사하지 않는다. `if (placements.isNotEmpty)` 가드와 `length >= 0` 같은 공허한 단언이 여럿이다.
- `SimulatorScreen` 2,652줄에 위젯 테스트가 0개. 페인터는 투영 수식만 테스트.
- Playwright는 1280×960 고정 좌표를 눈감고 클릭한다. 베이스라인이 없으면 자동 생성 후 PASS로 보고한다. `e2e/helpers/app-actions.ts`는 어떤 스펙도 쓰지 않는 죽은 코드다.
- 유사도 파이프라인은 SSIM을 계산하지 않고(라이브러리만 설치), 화면과 사진을 비율 왜곡해 늘린 뒤 밝기 히스토그램을 비교한다. 전체 35.4%로 스크립트 자체 기준(40% 미만 "매우 낮음")에도 미달이며, 렌더러가 이 지표에 맞춰 튜닝됐다.

## 7. 아키텍처 결정: 3D를 어떻게 만들 것인가

| 옵션 | 내용 | 장점 | 단점 | 예상 |
|---|---|---|---|---|
| A. CustomPainter 위 진짜 3D 코어 | 카메라 행렬(orbit·pitch·zoom), AABB 정확 정렬(위상 정렬), 법선 컬링, Lambert 조명, 정적 장면 Picture 캐시 | 의존성 0, 웹·모바일 동일, 리스크 최저, 기존 Flutter 지식으로 가능 | 포토리얼 불가, 그림자는 근사, 트렁크 곡면은 저폴리 | 1~1.5주 |
| B. flutter_scene 0.23 | 실제 메시·조명·glTF, 웹은 WebGL2 백엔드 | 진짜 3D, 나중에 실사 트렁크 모델 가능 | pre-1.0 API 변동, 네이티브는 Flutter 3.47+ 필요(현재 설치 3.35.1이라 업그레이드 선행), 피킹·드래그 레이캐스트 직접 구현, 쏘렌토 트렁크 3D 모델링 필요 | 2~3주 + 모델링 |
| C. three_js Dart 포트 | Three.js 변환 패키지 | 기능 많음 | 패키지 11개 의존, 알려진 이슈 다수, 웹 추가 스크립트 필요 | 비추천 |
| D. React + react-three-fiber로 전환 | 웹 네이티브 3D | 생태계 최강, 공유·SEO 유리 | Flutter 코드 전면 폐기, 앱스토어 경로 재설계 | 4주+ |

추천: A로 1차 배포. 렌더러를 인터페이스(`SceneRenderer`: project, pick, draw) 뒤에 두어 B로 교체 가능하게 설계한다.
이유: 이 제품의 핵심 가치는 "맞는지 판정"이고, 캠퍼에게 필요한 건 회전해서 확인할 수 있는 깔끔한 다이어그램형 3D다(EasyCargo, 3DPACK 스타일). 지금까지 실사 흉내에 쓴 노력이 판정 정확도를 갉아먹었다.
단, 실사 3D(광고·공유 이미지 품질)가 1차 배포 요건이면 B로 가야 하며 일정은 두 배가 된다. 이 결정은 사용자 몫이다.
